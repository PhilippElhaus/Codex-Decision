# Codex Jev output

Codex Jev runs as a local Rust `PostToolUse` hook with one enabled flag for all supported tool output. This skill helps with setup and evidence review; invoking the skill does not activate filtering. The optional VS Code control enables Jev for a new local thread and preserves later on/off changes. Click **jev** to toggle; there is no integration popup. A standalone hook starts disabled until configured. The hook needs a user-provided TypeSafe AI API key and Codex trust for the current hook definition. On a surface without local hook execution, explain that limitation before recommending a setting.

## Set up or diagnose

1. Check whether `codex-jev` is installed and enabled in the current Codex environment. Identify the installed plugin's data directory and active Codex session before inspecting session activity; do not assume a path or session from another window. Run `jevctl check-hook-trust --cwd <repository>` after an update and review any changed hook in `/hooks`.
2. Use the single Jev toggle for the active thread. Supported output uses one shared relevance cutoff. Legacy switches merge to on if any was on; old cutoffs migrate to a relevance cutoff no higher than 5%. Explain that eligible text is sent to TypeSafe AI's Jev API. Do not enable filtering for output that may contain secrets or other text the user has not authorized sending to that service.
3. If a key is missing, direct the user to **Connect Jev** in the optional VS Code control or to the local key setup guide. Do not ask the user to paste a key into chat. Do not print, copy, or inspect the saved key.
4. Prefer **Monitor** while evaluating unfamiliar output. Each eligible result gets one Choice over a bounded sample. A valid excerptable class with at least 95% combined normalized probability across excerptable classes permits line-relevance batches bounded by the API context limits. Each candidate line receives a task-relevance Noul; only probabilities at or below the shared cutoff (5% by default) can be omitted. Protected diagnostics, context, completion evidence, representative duplicates and the last line stay intact. The second stage has no candidate-line cap. It packs complete targets under both Jev limits: 32k tokens for state plus the longest question and 64k for the whole request. The hook uses conservative UTF-8 byte-based token estimates plus 4,096 framing headroom because no official local tokenizer is published. Every eligible line belongs to exactly one batch. A later batch failure rolls back progress and keeps the full result. The pipeline has two stages, with one or more relevance calls after the Choice. There is no optional gate switch. A changed enabled flag, mode, or cutoff applies to the next result. The optional composer control needs a separately installed extension and pinned patch.


## Review a shortened result

Read the visible text and its omission map. If an answer depends on omitted lines, use the exact saved-original path supplied by that result, subject to the user's file access and privacy boundaries. Check the original line ranges before making a claim about missing failures, unique values, or search matches. Do not infer that omitted text is irrelevant solely from Jev's decision.

For a decision investigation, use the active session's private receipt and separate batch records or its activity summary without exposing raw tool output, API keys, or credentials in the response. The Rust `jevctl evaluate-quality --cases <reviewed-cases.json>` command reports actual evidence loss separately from proposed omissions and compares stricter gate trials without changing settings. Compact decisions may omit absent probability fields; those lines remain unjudged or protected. If the hook, API, storage, or answer validation fails, the expected behavior is to keep the full result; report observed behavior without claiming that Jev shortened it. Request count and judged-line count are different. Estimated tokens saved are character-based estimates, not billed tokens.

When enabled, the control is green when its small Jev API request succeeds, red when the key or request fails, and amber while it checks. Hook errors appear in the activity tooltip during a thread; the tooltip is hidden without a thread. After one minute without a hook receipt, the tooltip reports missing hook activity and explains recovery. Windows controls secure WSL UNC session directories as `700` and configs as `600`; older `755` session directories are repaired when opened. A normal skip still confirms that the hook ran. `line_budget` and `tool_input_budget` preserve oversized input before an API request; they do not indicate a failed key. The decision panel follows the focused composer, not a background view’s status messages. The button is gray when off or without a thread. The session's enabled flag, logs, statistics, and hook health live under `PLUGIN_DATA/sessions/<session-hash>/`; the key in `PLUGIN_DATA/.env` and behavior settings in `PLUGIN_DATA/settings.json` are shared by the installation.

Use the [installation guide](https://github.com/PhilippElhaus/Codex-Jev/blob/main/docs/setup/setup_installation.md) for platform-specific setup and the [data-handling guide](https://github.com/PhilippElhaus/Codex-Jev/blob/main/docs/architecture/design_data.md) for what can reach Jev and what stays local.

Use the [current batching verification](https://github.com/PhilippElhaus/Codex-Jev/blob/main/docs/development/batching_verification.md) to review measured behavior. The initial two-stage evaluation records the former single-request baseline. The historical 70/25 demo measures the retired questions and does not calibrate current relevance. Typed answers and passing fixtures do not establish safety for every future output. Do not silently apply trial cutoffs to installed sessions.
