# Local telemetry

`logs/model-requests.jsonl` separately records enabled-session model lifecycle observations and prepared-output metadata. It contains a hashed turn-and-agent key, mode, status, reported token/cache counts, and fixed outcome fields. It contains no model names, error text, commands, output, or claims. It uses the same 4 MiB bound, tail compaction, private-file checks, and no-delete behavior as filtering telemetry. These observations do not increment filtering counters.

Advisory provider calls write their own health ledger and content-free request metadata under `assistance/`. Filtering request metadata also includes reported `cached_tokens` and `cache_write_tokens`. Missing usage remains unknown. See [measurement](measurement.md) for the combined report.

When completion verification is enabled, `logs/completion-evidence.json` is a separate content-bearing snapshot. It is not telemetry. Its bounds, opt-in behavior, and retention are described in [completion verification](../reference/completion-verification.md).

The hook also writes content-free metadata to each enabled session's `logs/telemetry.jsonl`. Version 1 records an invocation start, each attempted provider request, and the terminal outcome with a random invocation ID. Start records contain the tool family, runtime, hook version, mode, provider, fallback setting, size limits, and relevance cutoff. Request records contain the stage, provider protocol, HTTP status when available, elapsed milliseconds, encoded request bytes, response bytes read, validated token usage when available, and a fixed outcome or error code. Completion records contain the skip or error code, output size, line counts, proposed omissions, prepared savings, and fallback use. Delivery remains `unverified`. These records contain no commands, task text, tool output, raw tool names, custom model names, endpoint URLs, credentials, or provider error messages.

Telemetry is local and enabled with the hook. Disabled hooks and errors before enabled session processing do not produce these records. Invocation timing starts after configuration selection and excludes the final metadata append. Each session retains at most 4 MiB, trimming to a complete tail of about 3 MiB before an append. With **Never delete logs** enabled, telemetry stops at its size limit and preserves existing records. Telemetry uses private regular files, a nonblocking lock, and no file sync. Lock contention, storage failure, process interruption, or a full log can leave gaps. Metadata failure cannot change a filtering result. Durable health and statistics remain the source for lifetime accounting.

Completed line evaluations also record `lines_relevance_below_cutoff`, `lines_restored_by_guards`, and `prepared_omitted_lines`. The first count includes judged eligible lines at or below the inclusive relevance cutoff before final representative and last-line guards. It excludes lines protected before judging. The second count records those below-cutoff lines that final guards kept. `proposed_omitted` counts final proposed removals after guards; `prepared_omitted_lines` counts removals only when a replacement was committed. Previews record zero prepared removals. Missing or failed evaluations leave these measurements unknown. These fields do not change the legacy `linesBelowOmitCutoff` statistics or verify delivery.

Run `node scripts/telemetry_audit.cjs --data-dir <absolute-PLUGIN_DATA> --since <UTC-ISO-timestamp>` to summarize retained metadata. Omit `--since` to use the full retained window. The audit reads only telemetry files and directory metadata. It emits aggregate counts, measurement coverage, HTTP outcomes, size bands, latency histograms, and missing invocation correlations. It exports no invocation IDs or local paths. It rejects malformed UTF-8, duplicate keys, and inexact integer tokens. It retries a changing file at most three times, then records an unstable-file gap. Latency percentiles are logarithmic bucket upper bounds. Window boundaries and retention can separate related rows, so the audit does not infer exact lifetime participation or treat missing rows as zero. Use the existing usage audit for durable counters and original-preservation checks.
