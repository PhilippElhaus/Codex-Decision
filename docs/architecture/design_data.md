# Data handling

Codex Jev uses independent line judgments. For each eligible physical source line, the Rust hook asks two Noul questions in a bounded shared request: **Can omit?** and **Exact text needed?** Search match and path lines receive a third **Task relevant?** Noul. Each answer applies to its own line. On general Output results that need at least two line batches, an optional Jev Choice check first asks whether filtering is useful. A Choice answer can only keep the full result or allow the line checks to proceed; it cannot authorize any deletion. The gate is enabled by default and can be turned off in session settings.

The three integration switches select exclusive input routes, not different Jev primitives. A disabled test/build or search/listing route leaves its recognized result intact even if Output is enabled. Such a skipped result sends no lines to Jev and adds no decision or statistics entry. Output handles other eligible tool text.

The request includes a bounded cue from the latest user task, the route and command, the target line, and short neighboring context. If the transcript task is unavailable, a bounded tool-input cue permits monitoring but never replacement. A request is capped at 28,000 serialized UTF-8 bytes and 250 target lines; the actual number of lines per request is normally much lower. Locally protected lines are skipped as targets, although bounded excerpts can provide neighboring context. At most 12 sequential batches run within the hook deadline. Lines beyond the budget remain unjudged and are kept. An invalid answer, failed request, sensitive-looking task, input, or result, unsupported format, or unsafe storage condition keeps the entire original result.

The Choice check samples at most 21 eligible lines across the beginning, middle, and end of the result, with each sample shortened to 180 characters. It returns `line_filter`, `keep_full`, or `uncertain`. The hook proceeds only when `line_filter` has at least 80% probability and 70% confidence and the complete distribution is valid. Otherwise it records `choice_kept_full_output` in this session's hook health and returns the full result. A failed or malformed Choice request records a hook error and returns the full result. This check adds one request only when multiple line batches would otherwise be needed; it can avoid those batches for prose and dense unique evidence.

Each line may be omitted only when `can_omit` is at or above the route's `omit_min` and `exact_needed` is at or below `exact_max`. The defaults are 95% and 5%. The optional search relevance guard adds a keep condition when its probability exceeds the configured cutoff; it starts disabled. Code also protects diagnostics, nearby context, completion totals, one representative of repeated lines, and the final line. A test/build result needs a completion marker. Search/listing accepts direct `rg`, `grep`, `find`, `fd`, `ls`, and Git search/listing results, as well as pure-text results from named local search tools. Numbered and JSONL records are validated before filtering. For `rg --json`, Jev judges a normalized `path:line:match` cue while retained records preserve original bytes. JSONL structure records are kept. Kept text is copied from the exact original UTF-8 byte spans, including ANSI escapes and line endings. ANSI cleanup affects only the text shown to Jev.

After each completed batch, the hook publishes a bounded version 3 panel snapshot with up to 250 judged lines from that batch, each with a short excerpt, action, omission probability, exact-text probability, optional task relevance, and keep reason. A later failed batch restores the previous snapshot. When a result is shortened, the hook first saves the exact original under `PLUGIN_DATA/outputs/<session-hash>/<call-hash>.txt`, then returns kept lines with omission counts and that path. Monitor mode records decisions without changing tool output. Replacement also requires at least 1,024 bytes and a 30% reduction. The original and visible result are stored once in a private receipt; separate private batch records contain each request, response, elapsed time, and target IDs. `PLUGIN_DATA/sessions/<session-hash>/stats.json` distinguishes HTTP requests from lines seen, judged, kept, omitted, protected, unjudged, and search relevance judged/kept. Logs, panel snapshots, settings, and hook health use that same private session directory.

The key is read from private `PLUGIN_DATA/.env` and sent in an HTTPS Authorization header. It is shared by the local installation and is not included in receipts, panel snapshots, or hook-health records. Receipts can contain raw tool output and task cues, so keep `PLUGIN_DATA` private. Managed receipts and batch records obey each session's log limit; saved originals remain until manually removed. Hosted tools and other calls that do not emit local PostToolUse events are unaffected. Metadata-bearing command objects can be judged but remain unchanged; the hook replaces only safe plain-string responses by default.

The package contains a prebuilt Linux x86_64 Rust hook and `jevctl`; no Python interpreter is needed at hook runtime. Other execution environments need a native hook build. The separately installed VS Code composer patch remains a version-pinned local development tool.
