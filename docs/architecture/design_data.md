# Data handling

Known independent-line formats use local validation and one or more relevance batches. Unknown formats first use one sampled Choice classification with the existing 95% combined branch gate. The selected provider receives one independent relevance question per eligible line. There is no per-line HTTP call.

One session `enabled` flag covers supported output. One shared `relevance_policy.relevant_max` controls omission and defaults to 5%. Code removes only candidate lines whose probability of being needed is at or below that cutoff. Exact and exhaustive content, prose, coupled structured data, and ambiguous output stay complete.

The first request includes the latest safe task cue, tool, bounded command, available exit code, line count, up to 21 evenly distributed samples, and up to 12 diagnostic samples. Samples contain at most 240 characters each. Each relevance batch includes complete target text and source order, nearby context, and bounded diagnostic/boundary anchors. Context-only text is capped at 500 characters per line. Source text is always data. Protected lines are not questions. The selected provider sees ANSI-cleaned text; retained output copies the exact original UTF-8 spans, including ANSI escapes and line endings.

The hook reads the full normalized latest safe user task through the bounded transcript reader. It checks one opened regular file and uses that same handle for the tail and fallback scan. Unix opens reject links and do not wait on a FIFO. It first reads the last 64 KiB, then can scan transcripts up to 50 MB with a 64 KiB record limit. An oversized, sensitive, empty, unsupported, or incomplete latest user record prevents requests; an older task cannot replace it. Missing task context permits preview, never replacement. Inputs above 10,000 physical lines or 256 KiB of serialized tool input stay complete before an API request. Short, sensitive, mixed-media, mutating, and unsupported tool results also stay complete. Sensitive-field checks include common password, API-key, token, and authorization delimiters in plain text, JSON, and XML; they are conservative pattern checks.

Both providers use local request caps based on the TypeSafe Jev 1.13 limits: 32k tokens for state plus the longest question, and 64k for the whole request. The local packer conservatively counts serialized UTF-8 bytes as potential tokens and reserves 4,096 units for service framing. It does not use a four-characters-per-token estimate. There is no 250-line or batch-count cap. See [the budget calculations](design_integrations.md#api-context-budgets). The official API has no published local tokenizer, so these bounds are estimates; API errors still keep the full original.

Every eligible line belongs to exactly one relevance batch. Explicit exhaustive tasks, exact source/diff reads, and impossible savings return before an API request. If even one complete target and its required context cannot fit, `relevance_budget` returns the full result before relevance. Batches never silently judge a truncated subset. Packing uses the previous window's target count as a hint and validates both limits again; wider windows shrink and narrower windows can grow. The evaluation budget remains 45 seconds. Each request uses the configured timeout, at most four seconds, and normal log locks wait at most two seconds. Rollback and error reporting each allow at most 250 ms of lock contention after the deadline. A failure or deadline in a later batch returns the full original and restores the previous panel state. No replacement or successful receipt is published before all batches succeed.

Responses require the exact question IDs, types, finite probabilities in [0,1], and a valid Decision model envelope. Duplicate JSON fields are rejected at every depth, including escaped spellings of the same field. Configuration, hook events, transcript records, and code-mode command envelopes use the same duplicate-field check. Choice distributions must include all eight classes, sum within 0.02 of one, and select a maximum-probability class. The branch calculation normalizes the rounded sum. predicate or Noul answers have no confidence field. Missing, extra, malformed, failed, or late answers keep the full original.

Local rules protect diagnostics (including WARN), neighboring context, complete indented backtrace continuations, completion totals, one representative of repeated lines, and the final line. Test/build adapters require completion evidence. Search adapters validate numbered records and supported JSONL. Unknown coupled structures stay complete even if classification suggests excerpting. Source and diff reads remain complete even when a source filename has no extension or summary flags accompany a patch. For known adapters, normalized model cues do not change retained original records.

A completed relevance batch can publish a version-6 snapshot containing every source line in order, including earlier judgments, protected lines, and pending lines. Outputs below 1,000 lines publish every batch. Larger outputs publish the first and final batches and intermediate updates at most once per second. Every completed judgment remains in the final snapshot and receipt. Judged rows carry actual task relevance. Protected and pending rows carry no probability. Snapshots are bounded to 10,000 lines and 8 MiB. The panel validates row counts against totals and can still read version-3/4/5 historical snapshots. Receipts use version 3; historical version-2 receipts remain readable. Private batch 0 exists only when classification ran; batches 1 through N record line judgments. Manifests record the class, actual request count, API token usage when supplied, elapsed time, policy, and line decisions. Kept classification-only results record their distribution and usage in activity events.

Replacement saves the exact original under `PLUGIN_DATA/outputs/<session-hash>/<call-hash>.txt` before returning retained spans, omission counts, and its path. Monitor leaves the result unchanged. Replacement needs a supported text response, actual user task, more than 256 bytes saved and more than a 20% reduction after all headers. A known command object or code-mode text array also saves its exact typed value in the adjacent `.json` file. The `.txt` file contains the complete readable view. Metadata stays protected in that view. Both paths appear in replacement feedback. Receipt, stats, and final snapshot publication remain transactional. Later telemetry failure cannot cancel a committed replacement. Saved originals remain until manually removed; managed logs obey existing retention limits.

Immutable batch evidence is encoded and synced to private pending files before the session lock. The transaction publishes those bytes under the lock. Panel rows are constructed before locking; their publication timestamp is set under the lock. Pending files are removed after completion. Crash recovery removes only recognized private regular files older than the hook's 60-second outer timeout. Fresh, unknown, linked, and nonregular files are preserved. A log folder on another filesystem uses the existing private atomic-write fallback.

Receipt, batch, and panel encoders borrow existing evidence. Their bounded writers preserve canonical JSON field order and stop at the existing byte limits. Buffer growth stays within those limits. Bulk receipt and panel bytes are prepared before the log lock. A serde marker records the timestamp byte range; it does not search source text. Publication inserts the locked UTC timestamp and checks the final size before writing. Source hashes and character counts are also computed before the lock. Source spans and diagnostic protection have frozen baseline parity checks. Unix directory creation applies mode 700 at creation, so concurrent initialization cannot observe a temporary public mode. Event and lock files must be regular files on the opened handle. Unix opens reject links and use nonblocking access.

Retention reads at most the last 1 MiB of the event log through one regular, no-follow handle. It keeps complete JSONL tail records. Receipt and batch pruning accepts only canonical managed filenames and, on Unix, private files owned by the current user. Unknown files, public files, links, and special files remain intact. Saved originals do not participate in automatic retention.

The selected provider key (`OPENAI_API_KEY` or `JEV_API_KEY`) is read from private `PLUGIN_DATA/.env` and sent in an HTTPS Authorization header. It is shared by the local installation and is not included in receipts, panel snapshots, or hook-health records. Receipts can contain raw tool output and task cues, so keep `PLUGIN_DATA` private. Directory checks reject linked roots, ancestors, sessions, and logs before access. This does not replace OS access controls or eliminate all races with another process running as the same user. Managed receipts and batch records obey each session's existing log limit; saved originals remain until manually removed. Hosted tools and other calls that do not emit local PostToolUse events are unaffected. Unknown metadata-bearing objects remain previews. Only validated command envelopes and supported text responses qualify for replacement.

The package contains a prebuilt Linux x86_64 Rust hook and `decisionctl`; no Python interpreter is needed for the hook, release checks, trust check, or pinned VS Code composer patch. Other execution environments need a native hook build. Browser capture and documentation tests remain development tools.

Code-mode results with known command envelopes can be shortened after independent-line validation. The hook decodes only validated fields, keeps metadata as protected lines, and saves the original text-item array as JSON. Unknown schemas, annotations, and mixed media remain complete. `continue: false` supplies model-visible feedback and does not reject the nested tool promise. See the [official hook contract](https://learn.chatgpt.com/docs/hooks#posttooluse).

Private health records count skip reasons since the upgrade. Stats distinguish candidate results, actual replacements, proposed omissions, and actual omissions. `decisionctl activity --data-dir <PLUGIN_DATA> --session <thread-id>` reads only aggregate files. It does not read a key, task, or raw receipt. Missing legacy counters remain unknown; they are not invented as zero.
