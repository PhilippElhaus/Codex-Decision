# Data handling

Codex Jev uses two stages with serial API requests. One Choice question classifies a bounded sample of each eligible result. Only an excerptable class with at least 95% combined normalized probability across the excerptable classes proceeds. The second stage packs one independent relevance Noul per candidate source line into one or more requests. There is no per-line HTTP call and no optional bypass of classification.

One session `enabled` flag covers supported output. One shared `relevance_policy.relevant_max` controls omission and defaults to 5%. Code removes only candidate lines whose probability of being needed is at or below that cutoff. Exact and exhaustive content, prose, coupled structured data, and ambiguous output stay complete.

The first request includes the latest safe task cue, tool, bounded command, available exit code, line count, up to 21 evenly distributed samples, and up to 12 diagnostic samples. Samples contain at most 240 characters each. Each relevance batch includes complete target text and source order, nearby context, and bounded diagnostic/boundary anchors. Context-only text is capped at 500 characters per line. Source text is always data. Protected lines are not questions. Jev sees ANSI-cleaned text; retained output copies the exact original UTF-8 spans, including ANSI escapes and line endings.

The hook reads the latest safe user task through the bounded transcript reader. It first reads the last 64 KiB, then can scan transcripts up to 50 MB with a 64 KiB record limit. An oversized or sensitive latest user record prevents requests. Missing task context permits preview, never replacement. Inputs above 10,000 physical lines or 256 KiB of serialized tool input stay complete before an API request. Short, sensitive, mixed-media, mutating, and unsupported tool results also stay complete.

Every request must fit both documented Jev 1.13 limits: 32k tokens for state plus the longest question, and 64k for the whole request. The local packer conservatively counts serialized UTF-8 bytes as potential tokens and reserves 4,096 units for service framing. It does not use a four-characters-per-token estimate. There is no 250-line or batch-count cap. See [the budget calculations](design_integrations.md#api-context-budgets). The official API has no published local tokenizer, so these bounds are estimates; API errors still keep the full original.

Every eligible line belongs to exactly one relevance batch. If even one complete target and its required context cannot fit, `relevance_budget` returns the full result after classification. Batches never silently judge a truncated subset. Packing uses the previous window's target count as a hint and validates both limits again; wider windows shrink and narrower windows can grow. The evaluation budget remains 45 seconds. Each request uses the configured timeout, at most four seconds, and normal log locks wait at most two seconds. Rollback and error reporting each allow at most 250 ms of lock contention after the deadline. A failure or deadline in a later batch returns the full original and restores the previous panel state. No replacement or successful receipt is published before all batches succeed.

Responses require the exact question IDs, types, finite probabilities in [0,1], and a valid Jev model envelope. Choice distributions must include all eight classes, sum within 0.02 of one, and select a maximum-probability class. The branch calculation normalizes the rounded sum. Noul answers have no confidence field. Missing, extra, malformed, failed, or late answers keep the full original.

Local rules protect diagnostics (including WARN), neighboring context, completion totals, one representative of repeated lines, and the final line. Test/build adapters require completion evidence. Search adapters validate numbered records and supported JSONL. Unknown coupled structures stay complete even if classification suggests excerpting. For known adapters, normalized model cues do not change retained original records.

A completed relevance batch can publish a version-5 snapshot containing every source line in order, including earlier judgments, protected lines, and pending lines. Outputs below 1,000 lines publish every batch. Larger outputs publish the first and final batches and intermediate updates at most once per second. Every completed judgment remains in the final snapshot and receipt. Judged rows carry actual task relevance. Protected and pending rows carry no probability. Snapshots are bounded to 10,000 lines and 8 MiB. The panel validates row counts against totals and can still read version-3/4 historical snapshots. Receipts use version 3; historical version-2 receipts remain readable. Private batch 0 records classification; batches 1 through N record line judgments. Manifests record the class, actual request count, API token usage when supplied, elapsed time, policy, and line decisions. Kept classification-only results record their distribution and usage in activity events.

Replacement saves the exact original under `PLUGIN_DATA/outputs/<session-hash>/<call-hash>.txt` before returning retained spans, omission counts, and its path. Monitor leaves the result unchanged. Replacement also needs a safe plain-string result, actual user task, at least 1,024 bytes saved and a 30% reduction. Receipt, stats, and final snapshot publication remain transactional. Later telemetry failure cannot cancel a committed replacement. Saved originals remain until manually removed; managed logs obey existing retention limits.

The key is read from private `PLUGIN_DATA/.env` and sent in an HTTPS Authorization header. It is shared by the local installation and is not included in receipts, panel snapshots, or hook-health records. Receipts can contain raw tool output and task cues, so keep `PLUGIN_DATA` private. Directory checks reject linked roots, ancestors, sessions, and logs before access. This does not replace OS access controls or eliminate all races with another process running as the same user. Managed receipts and batch records obey each session's existing log limit; saved originals remain until manually removed. Hosted tools and other calls that do not emit local PostToolUse events are unaffected. Metadata-bearing command objects can be judged but remain unchanged; the hook replaces only safe plain-string responses by default.

The package contains a prebuilt Linux x86_64 Rust hook and `jevctl`; no Python interpreter is needed for the hook, release checks, trust check, or pinned VS Code composer patch. Other execution environments need a native hook build. Browser capture and documentation tests remain development tools.

Code-mode orchestration results are preview-only. The hook decodes the `output` field of a known command-result text envelope for line judgments; its other fields remain in preview context. It does not decode unknown schemas or mixed-media arrays. The original `exec` or `wait` result is never replaced, even with explicit MCP replacement permission.
